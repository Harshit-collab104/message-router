## Product decisions to settle during implementation

These are unresolved by the inspected materials; they do not block documenting the present state.

- Who owns `user_id` for each live integration: a registered recipient, incoming phone sender, or business account? Which personal/group message sources are actually available to the product?
- What is the authoritative precedence among scam safety, verified OTPs, direct mentions, urgent messages, muted groups, promotional opt-out, and DND? Can highly urgent messages bypass quiet hours?
- Does `notify` mean an actual outbound message, a device push, or only a decision for an upstream consumer? If it is only a decision API, revise the README delivery claims accordingly.
- Is digest generation a preview, a consuming API response, or a delivery attempt? Which provider states count as accepted versus delivered, and what retry guarantee is expected?
- Should any cross-user material ever be used? Current channel/global fallback accesses private history; any shared examples would need a distinct explicitly permitted corpus, not an ownership-filter escape.
- Which Python/deployment environment and data sources are supported? Should the legacy challenge submission workflow be maintained or retired?

No live account credentials, provider setup, or implementation permission is required to review this backlog. External integration checks should be explicit, opt-in validation after the corresponding offline behavior is correct.

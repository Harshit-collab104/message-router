## Smallest repair sequence

Keep these as separate reviewable patches. Fix the observed boundary rather than undertaking the full architecture backlog. This is a proposal only; none of the repairs below was applied.

1. **Close the two P0 data boundaries.** Add a fail-closed credential/authorization dependency to private/admin APIs and provider authenticity checks before webhook parsing causes side effects. Do not introduce an entire account system just to protect the current single-owner/admin console; define that access boundary explicitly. Keep user ownership in every RAG fallback and reject foreign metadata/evidence. Remove private channel/global fallbacks instead of tuning their distances. Convert the six access/retrieval cases to rejection/empty-owned-context assertions. Browser escaping and Docker context exclusions remain independent pre-deployment tasks from the audit.
2. **Repair the three cold-entry paths with existing accessors.** Read `get_message_history()` and `get_message_events()` into local variables inside prompt compilation; read `get_messages()` inside batch; import/use the event/history getters in the server handler. Preserve schemas and output ordering. Handle absent batch input/template explicitly rather than hiding the next exception. Convert the four cold-path cases to valid prompt/history results or a documented input error. No service split or database replacement is needed.
3. **Share mandatory routing policy and one retrieval context.** Extract/reuse a small deterministic policy evaluator around every engine; do not call the whole heuristic before every LLM just to reuse its security checks. Fix mention recognition, separate trusted OTP typing from scam detection, and remove the bare-leak credential-theft rule. Apply the DND flag once and pass the same authorized, cutoff-filtered retrieval result to the prompt, heuristic, and trace. Convert the seven provider-policy/cutoff/DND/mention/OTP/leak cases to the agreed expected behavior. Settle urgent/mention/DND precedence without redesigning all notification preferences.
4. **Make digest state truthful before adding scheduling.** Check outbound HTTP status, preserve a normalized failed/skipped result, and update delivery state only after the defined success condition. Recommended `auto_send=False` behavior is a non-consuming summary; a consuming API-response contract needs a distinct state/name. Convert the four digest cases to retained pending work or truthful success. Moving the update fixes the reproduced loss, but alone does not solve concurrent dispatch or a crash after sending and before committing. Add a small durable claim/attempt record before promising retry-safe automatic delivery; do not claim exactly-once delivery from the reorder alone.
5. **Handle one source event once and repair the Groq call site.** Define the recipient/source/message-ID receipt key, add its uniqueness migration, and reuse the stored decision on replay; handle concurrent duplicate inserts too. An application-only existence check is insufficient. For Groq, share the existing Requests key/model/timeout plumbing in a small transport helper usable for routing JSON and digest text; do not import an imaginary SDK client or reuse a routing-result tuple as summary text. Convert the replay and Groq cases to one decision and an actual mocked transport call.

These groups cover all 23 cases (6 + 4 + 7 + 4 + 2). The safest execution order within the P0 group is ingress access restriction, then retrieval ownership. The shared safety policy should follow immediately; initialization fixes are small and make its prompt-path regressions reliable. No new provider SDK, worker framework, frontend redesign, or storage replacement is needed to resolve these reproductions.
